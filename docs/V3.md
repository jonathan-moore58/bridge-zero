# The vault on the Portaldot V3 testnet

What a user of [`PortaldotVault`](../contracts/src/bridge/PortaldotVault.sol) needs to know about
the V3 testnet, and how to deploy, lock in and read the vault with `npm run v3-vault` (in `relayer/`,
[`relayer/src/v3-vault.ts`](../relayer/src/v3-vault.ts)), and how the committee releases from it on
the trusted return path with `npm run release` ([`relayer/src/release.ts`](../relayer/src/release.ts)).
Why the vault is built this way is in [DECISIONS.md](DECISIONS.md). Measured on Oct 19, 2026, the
release on Oct 20.

## The testnet

| | |
|---|---|
| Substrate RPC | `wss://test-node-v3.portaldot.dev` |
| EVM RPC | `https://test-evm-rpc-v3.portaldot.dev` (eth-rpc `main-fddd431`) |
| Genesis hash | `0xd4f9acbcf7f52388d8b095abe3c198d19fc510e0343e643e87cfbccb155283bd` |
| Runtime | portaldot-v3, spec 3002 |
| Chain id | 420420777 (`0x190f1ca9`), in pallet-revive and the EVM RPC |
| Blocks | every 6 s, finalized by GRANDPA (2 validators); the EVM RPC serves the state of about the last 256 blocks ("State already discarded" for older ones), while the Substrate node served older state when checked on Oct 20 |
| tPOT | 14 decimals, existential deposit 0.1 tPOT, SS58 prefix 42 |
| `NativeToEthRatio` | 10,000: EVM values (`msg.value`, `eth_getBalance`) have 18 decimals. `eth_getBalance` reports the reducible balance, without the existential deposit (an account holding 200 tPOT shows 199.9) |
| pallet-revive | `AllowEVMBytecode` true; `DepositPerByte` 0.06 tPOT, `DepositPerItem` 0.15 tPOT, `DepositPerChildTrieItem` 0.0015 tPOT; `CodeHashLockupDepositPercent` 30%; `GasScale` 5; `AutoMap` on (an account is mapped to its address when it is created) |
| pallet-multisig | `DepositBase` 5.43 tPOT, `DepositFactor` 1.92 tPOT |
| Gas price | about 39,600 wei per gas: `eth_gasPrice` is the base fee, and the priority fee is 0 |

On the EVM RPC, `eth_estimateGas` includes the storage deposit in the gas, so gas times gas price is
the whole cost of a transaction. `eth_call` takes a state override set as its third parameter;
`eth_estimateGas` ignores one, and `eth_simulateV1` is not available. `eth_getBlockByNumber` serves
only recent blocks, while `eth_getLogs` also returns older logs.

## Costs

Every new contract storage item, a 32-byte key and a 32-byte value, takes a deposit of
0.06 × 64 + 0.0015 = 3.8415 tPOT from the account that sends the transaction, and gives it back when
the item is cleared. Code is charged by the byte as well: a dry run of the vault's deployment charges
83.232 tPOT.

| What | Storage deposit | Other cost | Paid by |
|---|---:|---|---|
| Deploying the vault (899 bytes of code) | 83.232 tPOT | fee about 0.13 tPOT | the deployer |
| The first lock: `commitments[0]`, `nextNonce` and `outstanding` are new | 11.5245 tPOT | fee about 0.023 tPOT | the locker |
| Every later lock: its `commitments[nonce]` | 3.8415 tPOT | fee about 0.023 tPOT | the locker |
| A lock while `outstanding` is 0 again | 7.683 tPOT | fee about 0.023 tPOT | the locker |
| A release: `released[burnId]` | 3.8415 tPOT, 0 net when it brings `outstanding` to 0 (that slot is cleared); the call's deposit limit must still allow 3.8415 | 0.1 tPOT more when the payee account does not exist yet; weight about 0.78 × 10^9 ref time and 26,000 proof size | the multisig account |
| A multisig approval round | `DepositBase` + 2 × `DepositFactor` = 9.27 tPOT, held until the call runs | the fee of each approval: about 0.0328 tPOT to open a release, 0.0336 to run it (Oct 20) | the member who opens it, each member |

The deploy figures come from the `reviveApi.instantiate` dry run and `payment_queryInfo`; the lock
and release figures from `reviveApi.ethTransactWithConfig` dry runs of the transactions against the
V3 build, placed at the vault's address by a state override. As an Ethereum transaction, a first
lock estimates at about 2.92 × 10^14 gas and a later one at about 9.8 × 10^13.

## Deploy

```
cd contracts
FOUNDRY_PROFILE=v3 forge build --skip test --skip script
cd ../relayer
npm run v3-vault -- deploy --releaser 0xA08A7f7DEd49CC81F901Fb42Fec00edFC48c0fc1 --committee-multisig 5FTrjzEPPdxo3WP1RcQGTzUX1y1udD7tAkaETV1iLH24xPk3
```

That is a dry run; nothing is signed. It refuses a build older than the source or not from the v3
profile, checks the genesis hash and the chain id, reads `NativeToEthRatio` live, checks that the
multisig is the committee's 2-of-3 account and that its address is `--releaser`, has the EVM RPC run
the constructor, and dry-runs the deployment (`reviveApi.instantiate`) from the deployer
(`5ERJiUnzmQwEF98X3rGyKiNsyjrcenLGJST3MULCjUSwgPJ7` unless `--from`). It prints the vault's address
(`0xa02EE16EB03d2cf1aeF199F7658FB8c8E3188ffd` while the deployer's nonce is 1), the deposit, the
weight, the fee and the deployer's balance. With `--send --key-file <path>` (a JSON file with
`.substrate.mnemonic`, whose account has to be the deployer; the tool never prints it) it signs and
submits the extrinsic, waits for finalization, checks `ExtrinsicSuccess`, `revive.Instantiated` and
the deployed code, and writes the vault to `deployments/v3-testnet.json`. It refuses to deploy a
second vault over a recorded one.

## Lock

```
npm run v3-vault -- lock --dst-chain 11155111 --dst-minter <minter on Sepolia> --recipient <address on Sepolia> --amount 1.5
npm run v3-vault -- lock --dst-chain 11155111 --dst-minter <minter on Sepolia> --recipient <address on Sepolia> --amount 1.5 --send --account bz-deployer --password-file <path>
```

`--amount` is in tPOT, with at most 14 decimals; the value sent is the amount in 18-decimal EVM
units. The dry run (the first line, from `0xD9838A86cF83C28Ee486544060D1cA4Ca2971071` unless
`--from`) prints the nonce the lock gets, the commitment the vault will store and its slot, the gas
and the fee. `--send` signs with the Foundry keystore through cast and sends an EIP-1559 transaction
(no priority fee, max fee one eighth above the gas price), records it in
`deployments/v3-testnet.json` before publishing it, and checks the `Locked` event and the stored
commitment.

A lock commits to its destination: only the `BridgeMinter` it names, on the chain it names, can
prove it, and the vault never gives a lock back (it pays out against burns only). So the dry run
fails, and `--send` refuses, unless `--dst-chain` and `--dst-minter` are the `chainId` and
`contracts.BridgeMinter` of a `deployments/*-bridge.json` whose vault is this one (today
`deployments/sepolia-bridge.json`: 11155111 and `0x8287B3Baf205CA8456f98346F13064AA7fCDcB9E`, and
`deployments/base-sepolia-bridge.json` and `deployments/arbitrum-sepolia-bridge.json`: 84532 and
421614 with `0xdc31a3BC1354545EeB985AaD7b2Aa662E9272348`; only Sepolia's has a mint path today);
`--any-destination` makes that a warning. It fails too for a recipient that is a Substrate
account's address on V3 (`revive.originalAccount` maps it to one, read from the node; a lock from a
Substrate account also refuses that account's own address): no Ethereum key holds such an address,
so wtPOT minted there could never move or be burned.

From a wallet instead: add the network (chain id 420420777, RPC
`https://test-evm-rpc-v3.portaldot.dev`, currency tPOT with 18 decimals) and call
`lock(uint256 dstChainId, address dstMinter, address recipient)` with the amount as value. The value
has to be a whole number of native base units, a multiple of 10^4 wei, or the vault reverts with
`DustNotAllowed`.

From a Substrate account (a `5…` address, as the app's Portaldot Wallet path locks):

```
npm run v3-vault -- lock --dst-chain 11155111 --dst-minter <minter on Sepolia> --recipient <address on Sepolia> --amount 0.001 --from <ss58>
npm run v3-vault -- lock --dst-chain 11155111 --dst-minter <minter on Sepolia> --recipient <address on Sepolia> --amount 0.001 --send --key-file <path>
```

The lock is then `revive.call(vault, amount, weight limit, storage deposit limit, lock calldata)`:
the value is the amount in native base units, and the vault's `msg.sender` is the account's address,
keccak-256 of its account id (pallet-revive maps it). The dry run is `ReviveApi_call` from the
account, whose weight plus 10% and storage deposit plus 2% become the limits; `--send` signs with the
key file (`deploy`'s format, or a polkadot-js keystore with `--password-file`), records the
extrinsic before submitting it, and once it is final checks `ExtrinsicSuccess`, the vault's `Locked`
event and the stored commitment. Such a lock's `Locked` event is a `revive.ContractEmitted` event in
`System.Events`, not a log: V3's EVM RPC indexes the logs of Ethereum transactions only, so
`eth_getLogs` does not return it. Lock 3 (0.001 tPOT, Oct 27, extrinsic `0x953fc65c…4627b7f7` in
#222,024) was sent this way; `relayer/src/substrate-locks.ts` finds such a lock from its nonce (the
block where `nextNonce` passed it, then that block's events) for auto-mint, the mint tool and both
status commands.

## Read

```
npm run v3-vault -- status
```

This prints `nextNonce`, `outstanding`, the vault's balance and every lock and release from its logs,
with each commitment recomputed and compared with the event and with storage. A nonce below
`nextNonce` with no `Locked` log, a lock sent as a Substrate extrinsic, is read from `System.Events`
and counted like the others.

The storage layout is part of the protocol:

| Slot | Variable | Getter |
|---:|---|---|
| 0 | `mapping(uint256 => bytes32) commitments`: entry `nonce` at `keccak256(abi.encode(nonce, 0))` | `commitments(uint256)` |
| 1 | `uint256 nextNonce` | none: `eth_getStorageAt(vault, 1)` |
| 2 | `uint256 outstanding`, native base units locked and not released | `outstanding()` |
| 3 | `mapping(bytes32 => bool) released`: entry `burnId` at `keccak256(abi.encode(burnId, 3))` | `released(bytes32)` |

`NATIVE_TO_ETH_RATIO` and `RELEASER` are immutables without getters: they sit in the deployed code
at the build's immutable references, and `deployments/v3-testnet.json` records them.

- Commitment: `keccak256(abi.encode(keccak256("BridgeZero.Lock.v1"), 420420777, vault, dstChainId,
  dstMinter, recipient, amountNative, nonce))`.
- `Locked(uint256 indexed nonce, address indexed sender, address indexed recipient, uint256
  dstChainId, address dstMinter, uint256 amountNative, bytes32 commitment)`, topic
  `0x56431a42ac501689c7bf63a9cab5bc9a191019a6321793149852e1bbe6db157c`.
- `Released(bytes32 indexed burnId, address indexed to, uint256 amountNative)`, topic
  `0xc8fa66dff4b9073528c3f1bf21a8dc9a18fdf09847e88e96188bc953aef519f0`.

## Release (trusted)

The return path is trusted: the committee's 2-of-3 multisig account `5FTrjz…xPk3` (address
`0xA08A…0fc1`) is the only caller the vault accepts, and it can release up to `outstanding` to any
address. Two members approve `multisig.asMulti` with the call `revive.call(vault, 0, weight limit,
deposit limit, release(burnId, to, amountNative))`; `amountNative` is in native base units, and the
vault pays `amountNative × 10^4` wei. The burn id is
`keccak256(abi.encode(keccak256("BridgeZero.Burn.v1"), srcChainId, srcMinter, burnNonce))`, from the
burn the committee approves; the vault releases each id once.

The multisig account was funded with 20 tPOT on Oct 19 (V3 #101,134) and holds 16.1585 tPOT after
the first release, enough for the storage deposit of four more, and is mapped
to its address: `revive.originalAccount(0xA08A…0fc1)` names it, so a dry run from either form of
the origin runs as the vault's `RELEASER`. Each release needs at least 3.9415 tPOT of it, besides
the existential deposit. The members pay the fees of their approvals, and the member who opens a
release reserves 9.27 tPOT until it runs; members 1 and 2 were funded on Oct 20 (README rows 48
and 49), and member 3 holds none.

Before approving a release:

- Give `revive.call` a storage deposit limit of at least 3.8415 tPOT, 3.9415 when the payee account
  does not exist yet (the origin pays its existential deposit). The limit is needed even for the
  release that brings `outstanding` to 0, whose net charge is 0: the dry run reports a maximum of
  3.8415. A lower limit fails the whole call and the 2-of-3 round has to be redone.
- `to` must be an address someone controls: one derived from an Ethereum key, or the address of a
  Substrate account that already exists (`revive.originalAccount(to)` names it). The address of a
  Substrate account that does not exist yet pays a fallback account nobody controls.
- tPOT that reaches the vault's account outside `lock` belongs to no claim and cannot be released:
  `outstanding` counts locks only.

### With the release tool

`npm run release` in `relayer/` ([`relayer/src/release.ts`](../relayer/src/release.ts)) takes a
burn on Sepolia through these steps; [BRIDGE.md](BRIDGE.md#the-trusted-return-path) has the
commands in order.

```
npm run release -- release --burn-nonce <n>
npm run release -- release --burn-nonce <n> --approve --member <1|2|3> [--send --key-file <member json> --password-file <path>]
npm run release -- release --burn-nonce <n> --rehearse --amount <wtPOT> --to <h160>
npm run release -- fund --member <1|2|3> --amount <tPOT> [--send --key-file <path>]
npm run release -- status
```

- **The burn.** It reads `BurnRequested(n)` at Sepolia's finalized block and requires its burn id to
  be `burnIdOf(n)` and the convention above; the payee is the burn's `v3Recipient`, the amount its
  amount. `--rehearse` stands in for a burn that is not on Sepolia yet: the vault does not look at
  Sepolia, so the V3 side runs in full.
- **The vault.** At V3's finalized head, through `reviveApi.getStorage`: `released[burnId]` must be
  false and `outstanding` at least the amount. The vault's code must be the recorded one, and the
  committee's multisig must be its `RELEASER`, mapped to it.
- **The payee.** It must be a mapped Substrate account, a contract on V3, or an address that has
  sent transactions as a key does: the burn's own sender, or one with a nonce above 0 on Sepolia or
  V3, where it has no code (a contract on Sepolia, a smart wallet say, is no key's on V3; an
  EIP-7702 delegation still is). Anything else is refused, as nothing shows that anyone controls it.
- **The dry run.** `reviveApi.call` of the release from the multisig gives the weight and the
  storage deposit (782,299,332 ref time, 26,093 proof size and 3.8415 tPOT for 0.5 tPOT to
  `0xD983…1071` on Oct 20), and `reviveApi.traceCall` with the call tracer shows the `Released` log
  and the payout of `amount × 10^4` wei to the payee.
- **The limits.** Twice the dry run's weight, rounded up to 10^8 ref time and 10^4 proof size
  (1,600,000,000 and 60,000), and a storage deposit limit of the dry run's maximum + 2%, rounded up
  to 0.0001 tPOT and at least 3.9415 tPOT. The approvals come minutes apart, and the rounding makes
  every approver who dry-runs the same state build the same call, whose hash pallet-multisig keys
  the operation by. The release is dry-run again with these limits before anything is approved.
- **pallet-multisig on V3** (runtime 3002's metadata): `asMulti(threshold, other_signatories,
  maybe_timepoint, call, max_weight)`, `approveAsMulti(threshold, other_signatories,
  maybe_timepoint, call_hash, max_weight)` and `cancelAsMulti(threshold, other_signatories,
  timepoint, call_hash)`; its storage is `multisig.multisigs(account, call hash)` with the
  operation's timepoint, deposit, depositor and approvals. It stores no call: the call is on chain
  only in an extrinsic that carries it. So the first approval is `asMulti` with the call in full
  and no timepoint (it opens the operation, `NewMultisig`), not `approveAsMulti`, which would leave
  only the hash; the second is `asMulti` with the timepoint `multisig.multisigs` holds and the call
  in full, which runs it (`MultisigExecuted`, carrying the call's result: the extrinsic succeeds
  even when the call fails). With 2 of 3 there is no approval in between, so no `MultisigApproval`.
  `max_weight` has to cover the call's dispatch weight (`MaxWeightTooLow` otherwise): the tool takes
  it from `transactionPaymentCallApi.queryCallInfo`, 2,106,623,000 ref time and 67,725 proof size
  for the call above. `other_signatories` lists the other two members in ascending order of their
  account ids: `5EJJ…, 5F99…` for member 1, `5DLn…, 5EJJ…` for member 2, `5DLn…, 5F99…` for member 3.
- **The second approver** finds the operation in `multisig.multisigs` and its call in
  `deployments/v3-testnet.json` or in the opening extrinsic at its timepoint, and approves that call
  when it is this burn's release with limits that still cover the dry run; one that does not is
  cancelled by its opener (`--cancel`) and opened again.
- **After the release** the tool checks `MultisigExecuted` with result `Ok`, the vault's event
  (`revive.ContractEmitted`, `Released(burnId, to, amountNative)`), `released[burnId]`,
  `outstanding` and the payee's balance through `eth_getBalance`. V3's EVM RPC serves the logs of
  Ethereum transactions; for this Substrate extrinsic `eth_getLogs` may not return the `Released`
  log, and the tool says whether it does.
- `deployments/v3-testnet.json` records each round (`releases`: the burn, the call and its hash,
  the dry run, the multisig's timepoint, each approval written before it is submitted, then its
  block and events) and each funding transfer (`committeeFunding`).
